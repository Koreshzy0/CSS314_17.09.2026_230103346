### Analytical & Forensic Engineering Responses

- **Question 1 (GPU Coalescing vs. CPU Cache-Line Granularity):** The row pitch is 258 × 8 = 2,064 B, so consecutive elements of `u[1:257, 1]` are 2,064 B apart. On the host, a 64-B line holds 8 doubles, but a column walk touches a new line per element: 256 lines × 64 B = 16,384 B moved for 2,048 B useful (8× amplification). On the T4 each 8-B load in a strided warp lands in its own 32-B L2 sector: 256 × 32 B = 8,192 B for 2,048 B useful (4× amplification, 6,144 B wasted per column, 12,288 B for both columns per step). Without `pack_halos_kernel` a column would leave the device as 256 separate 8-B DMA pieces (or a `cudaMemcpy2D` with 8-B width and 2,064-B pitch). The kernel performs the strided gather once inside device DRAM and the PCIe transfer becomes one contiguous 2,048-B copy per halo (4 × 2,048 = 8,192 B per step), avoiding the wasted sector traffic and 256 DMA descriptors.

- **Question 2 (Shared-Memory Tile Synchronization & PTX Audit):** `tiled_stencil_kernel.inspect_asm()`: `st.shared.f64` = 5, `ld.shared.f64` = 5, `bar.sync` = 1 (one centre store plus four halo stores; five stencil reads; one `syncthreads`). A 16 × 16 block has 256 threads = 8 warps (warp w holds rows ty = 2w, 2w+1). A thread at row ty reads `tile[ty+2, tx+1]`, which was written by the thread at row ty+1, often in the next warp (e.g. ty = 1 is in warp 0, ty = 2 in warp 1). Warps run independently, so without `cuda.syncthreads()` there is a Read-After-Write hazard: the reading warp may load stale or uninitialised shared memory before the writing warp executes its `st.shared`, producing nondeterministic stencil results (also at the halo cells on tile edges).

- **Question 3 (Dual-Stream Compute-Communication Overlap on Shared GPU Silicon):** `gpu_serialized_ms` = 1500 ms and `gpu_overlapped_ms` = 1300 ms for 300 steps (speed-up = 1.15×). The gain is small because four MPI processes on one T4 each own a separate CUDA context; without MPS the contexts are time-sliced, so kernels from different ranks do not run truly concurrently, and all D2H/H2D copies share one PCIe link and a few DMA copy engines, so overlapped copies queue behind each other. The halo path is staged (device → pinned host → MPI shared-memory copy → pinned host → device). With four dedicated GPUs every rank has its own PCIe link and copy engines, and GPUDirect RDMA/P2P lets the NIC or peer GPU DMA directly from device memory, removing host staging, so overlap hides communication much better.

- **Question 4 (MPI-3 Shared-Memory MESI RFO Ping-Pong):** Latencies = stride 1 (8 B): 1500 ms, stride 8 (64 B): 120 ms, stride 16 (128 B): 115 ms; false-sharing slowdown = 12×. With stride = 1, `shm_view[0]` and `shm_view[1]` share one 64-B line. Trace: line initially I (or E in one core). Rank 0's core A writes `shm_view[0]`: it issues an RFO, other copies go to I and A holds the line in **M**. Rank 1's core B writes `shm_view[1]`: B's RFO snoops A; A's M line is forwarded/written back and goes **M → I**, B goes **I → M**. Rank 0's next write misses again: B **M → I**, A **I → M**. Every update pays a cache-to-cache transfer even though ranks touch different words. If a core only reads, the holder goes M → S and the next write needs another invalidation S → I. The LLVM audit (= 1 `load atomic`, = 1 `store atomic` in the loop) shows each update really goes to memory, i.e. nothing was hoisted into a register.

- **Question 5 (128-Byte Spatial Prefetcher Pairing & Padding Trade-Offs):** stride 8 (64 B) = 120 ms vs stride 16 (128 B) = 115 ms (ratio = 1.04×). The adjacent-cache-line (spatial) prefetcher treats memory as 128-B aligned pairs of 64-B lines (even/odd) and tends to fetch the buddy line along with the demanded one. At stride = 8 a rank's buddy line may still be pulled in or invalidated by a neighbour, leaving some residual coherence traffic; at stride = 16 each rank owns a whole 128-B sector, which removes it. The cost of over-padding is footprint: each useful 8-B counter occupies 128 B (16× expansion), so with many counters fewer useful words fit in L1/L2 and capacity/conflict misses grow, and the buddy-line prefetch is wasted bandwidth. With only four counters the footprint is negligible, so the extra gain is small.

- **Question 6 (CFL Stability & Distributed Energy Dissipation):** Δx = 1/513 == 1.9493 × 10⁻³, Δx² = 3.7998 × 10⁻⁶. κ is built in [1, 3], so κ_max = 3.0. Δt_max = Δx² / (4 κ_max) = 3.7998 × 10⁻⁶ / 12 = 3.17 × 10⁻⁷. The simulation uses Δt = 0.8 · Δt_max = 2.53 × 10⁻⁷ < Δt_max, so the explicit scheme satisfies the Courant condition. Global energy E = Σu²Δx² from `cart_comm.allreduce` = step 0: 0.01131, step 100: 0.01100, step 200: 0.01071, step 300: 0.01043 (serialized and overlapped agree). The decrease comes from diffusion through the Dirichlet boundary region and the λ = 0.15 damping; the small localized source adds a negligible amount.
